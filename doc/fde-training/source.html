第二部分　FDE 角色认知

2.1 官方定义：FDE 做什么

FDE 隶属 Anthropic 的 Applied AI 部门（与销售、产品、研发并列的独立部门）。根据 Anthropic 官方招聘页，FDE 的核心职责包括（英文为招聘页原文）：

招聘页原文解读
Work within customer systems to build production applications with Claude models, ensuring that these products meet customer requirements.在客户的系统里构建生产级应用，而不是做 Demo 或 PPT。
Deliver technical artifacts for customers like MCP servers, sub-agents, and agent skills that will be used in production workflows.三类标准交付物：MCP Server、子代理（Sub-agent）、Agent Skill。课程 M3、M4、M5/M6 分别对应。
Provide white glove deployment support for Anthropic products in enterprise environments.为 Claude Enterprise、Claude Code 等产品在企业环境中的部署提供“白手套”级支持（M8、M9、M10）。

FDE 负责人岗位（Head / Manager of Forward Deployed Engineering）的招聘页进一步说明了团队层面的目标：

Build repeatable delivery methodologies for MCP server development, Claude Code SDLC integration, custom agent development, and API product acceleration.
Architect multi-agent solutions, Centers of Excellence frameworks, and API integration patterns that become referenceable at Fortune 500 scale.

这四条“可复用交付方法论”是本课程的主线（见 3.2）。此外，多份招聘页提到 FDE 约有 25% 的时间在客户现场与客户一起构建，岗位经验要求从 4 年以上（Applied AI FDE）到 8 年以上（资深 / Staff 级）不等，要求“技术型、面向客户的角色”或“有咨询经验的软件工程师”背景。

FDE 的本质：把“模型能力”变成“客户的生产结果” FDE 不是纯咨询，也不是外包开发。他们在客户现场解决真实问题，并把在一线反复出现的需求和模式沉淀为可复用的方法与平台能力，反馈给产品和工程团队。好的 FDE 交付的是上线运行的系统 + 可衡量的业务指标 + 客户团队能自己维护的能力。

第四部分　模块详解

M0 平台全景与模型选型

学时：6阶段：基础对应认证：Claude Certified Associate: Foundations

学习目标

  • 能向客户讲清 Claude 的产品矩阵：Claude Developer Platform（API）、Claude Enterprise、Claude Code、Claude Cowork、Claude Tag（Claude in Slack）、Managed Agents。
  • 能根据任务特征（推理深度、时长、吞吐、延迟、成本）选择模型与 effort 档位。
  • 能说明各部署渠道（Claude API、Amazon Bedrock、Google Cloud、Microsoft Foundry、Claude Platform on AWS）的差别与选型依据。

核心知识点

模型官方定位价格（输入 / 输出，每百万 token）默认 effort
Claude Fable 5.2高难度推理与长周期 Agent 任务$8 / $40high
Claude Opus 5.5长时间运行的 Agent 编码与知识工作$4 / $20medium
Claude Sonnet 5.5速度与智能的最佳平衡$2 / $10high
Claude Haiku 5.5高吞吐、低延迟任务（分类、抽取、路由）起价 $0.10 / $0.50medium

四款模型均支持 1M token 上下文与 128K 最大输出，均采用自适应思考（Adaptive thinking）。数据来自官方 Models overview，价格以官方 Pricing 页面为准。

  • 选型原则：先用能力最强的模型跑通并建立 Eval 基线，再逐级降档测试，按“每个任务的成本”而非“每个 token 的价格”决策（Zendesk 案例中的原话：“You can’t just look at token price in isolation… You have to look at the cost per task.”）。
  • effort 参数：控制模型投入的思考量，是成本 / 延迟 / 质量的首要调节旋钮。
  • 部署渠道：客户已有云的数据驻留、采购与治理要求，往往决定了渠道选择（Zendesk、Brex 走 Bedrock；Shopify 走 Google Cloud；Jamf 通过 AWS Marketplace 采购 Claude Enterprise）。

必修资料

  • Models overview：platform.claude.com/docs/en/models/overview
  • Choosing a model：…/about-claude/models/choosing-a-model；Effort：…/build-with-claude/effort
  • Claude Academy：AI Fluency: Framework & Foundations；Claude 101（academy.claude.com）
Lab 0 · 模型对比实验　选取同一组 20 条真实业务样本（如客服工单），分别用 Haiku 5.5 / Sonnet 5.5 / Opus 5.5 在不同 effort 下运行，记录准确率、平均延迟、单任务成本，输出一页“选型备忘录”。
案例联动　Zendesk 用覆盖 15 项指标的内部测试系统评估多家模型，并在每次新模型发布时重跑；最终选择 Sonnet，理由之一是“做出决策需要的规划轮数更少”。

考核产出：选型备忘录（含数据表与推荐理由）。

M1 Claude API 与提示词工程

学时：10阶段：基础对应认证：Claude Certified Developer: Foundations交付方法论：API product acceleration

学习目标

  • 熟练使用 Messages API：多轮对话、系统提示词、流式输出、多模态输入（图片、PDF）、结构化输出、批处理（Batch）。
  • 掌握官方提示词工程技术，并能把它们组合成复杂的“生产级提示词”。

核心知识点

  • 清晰直接的指令、提供上下文与动机、使用示例（few-shot）、用 XML 标签组织输入、角色设定、让模型先思考再回答、输出格式控制（结构化输出）、长文档放在提示词前部。
  • 从教程到真实场景：官方 Real world prompting 课程强调把多种技术组合到复杂提示词中，并通过迭代修正失败样本。
  • 按模型代际调整：官方为每个新模型发布专门的提示指南（如 Prompting Claude Opus 5.5 / Sonnet 5.5），升级模型时需要复核提示词。

必修资料

  • Claude Academy：Building with the Claude API（academy.claude.com/courses/building-with-the-claude-api）——官方旗舰开发者课程，涵盖 API、提示词、工具使用、RAG、Agent 与 MCP
  • GitHub anthropics/courses：① Anthropic API fundamentals ② Prompt engineering interactive tutorial ③ Real world prompting
  • Prompting best practices：…/prompt-engineering/claude-prompting-best-practices
  • Cookbook：Classification、Summarization、RAG（anthropics/claude-cookbooks）
Lab 1 · 工单分类与信息抽取服务　输入客户工单（文本 + 截图），输出 JSON：类别、紧急度、涉及产品、建议回复要点。要求：① 用结构化输出保证 JSON 合法；② 用 XML 标签分隔指令与数据；③ 构造 3 条 few-shot 示例；④ 用 Batch API 跑完 500 条历史工单并统计准确率。
案例联动　Intercom 的客服 Agent Fin 基于 Claude，开箱平均解决率 51%，最高可达 86%，支持 45+ 种语言，响应时间从 30 分钟降至秒级——“提示词与产品体验”打磨的结果。

考核产出：可运行的服务 + 提示词版本记录（每次修改的原因与效果）。

M2 上下文工程（Context Engineering）

学时：6阶段：构建对应认证：Developer / Architect Foundations

学习目标

  • 理解“上下文是有限资源”，能为长周期 Agent 设计上下文策略。
  • 掌握提示缓存、压缩（Compaction）、上下文编辑、记忆工具（Memory tool）等平台能力。

核心知识点（摘自官方博客 Effective context engineering for AI agents）

  • 上下文工程是提示词工程的自然演进：关注的是在每一步推理时，如何策划和维护“最优的 token 集合”，包括系统提示、工具、示例、消息历史与外部数据。
  • 上下文腐化（context rot）：上下文越长，模型准确回忆信息的能力越会下降；Transformer 中 n 个 token 有 n² 个两两关系，模型存在“注意力预算”。
  • 指导原则：找到“能最大化期望结果概率的、最小的高信号 token 集合”。
  • 即时检索（just-in-time）与 Agent 式搜索：保留轻量标识（文件路径、查询、链接），需要时再通过工具加载，而不是一次性塞满上下文。
  • 长周期任务三件套：① 压缩（总结后在新上下文中继续）；② 结构化笔记（Agent 把进度写到上下文之外，如 NOTES.md / 记忆工具）；③ 子代理架构（子代理在干净上下文中深挖，只返回浓缩结果）。

必修资料

  • Effective context engineering for AI agents（Anthropic Engineering）
  • 文档：Prompt caching · Compaction · Context editing · Memory tool · Context windows
  • 博客：The components of agent memory
Lab 2 · 成本与延迟优化　给 Lab 1 的服务加上提示缓存（缓存系统提示与 few-shot 示例），对比开启前后的成本与首 token 延迟；再为一个长对话场景启用压缩，观察长任务的完成率变化。
案例联动　Notion 借助提示缓存将成本降低 90%、延迟降低最多 85%（官方案例数据）。

考核产出：优化前后对比报告（成本、延迟、质量三项指标）。

M3 工具设计与 MCP（Model Context Protocol）

学时：10阶段：构建对应认证：Developer / Architect Foundations交付方法论：MCP server development

学习目标

  • 能设计“对 Agent 友好”的工具接口，并用 Eval 驱动工具迭代。
  • 能独立开发、测试并部署一个企业内部数据的 MCP Server（FDE 三大标准交付物之一）。

核心知识点

工具设计原则（Writing effective tools for agents）

  • 选对工具：不要把每个 API 端点都包成工具；围绕高价值工作流设计少量、能整合多步操作的工具。
  • 命名空间：用前缀区分服务与资源（如 asana_search、jira_search），减少混淆。
  • 返回有意义的上下文：返回自然语言名称而非晦涩 ID；按需提供“简洁 / 详细”两种响应格式。
  • 节省 token：分页、范围选择、过滤、截断并设合理默认值。Claude Code 默认把工具响应限制在 25,000 token。
  • 像写给新同事一样写工具描述，并通过 Eval 不断改进；可以让 Claude 分析评测记录并自动改写工具。

规模化优化（Advanced tool use 与 Code execution with MCP）

  • 5 个 MCP Server 共 58 个工具，定义就占约 55K token；Anthropic 内部曾见过优化前达 134K token。
  • Tool Search Tool：按需发现工具，token 用量减少 85%；内部 MCP 评测中，Opus 4 准确率从 49% 提升到 74%，Opus 4.5 从 79.5% 提升到 88.1%。
  • 程序化工具调用：让 Claude 写代码编排多次工具调用，复杂研究任务平均 token 从 43,588 降到 27,297（-37%）。
  • Tool Use Examples：在复杂参数场景下准确率从 72% 提升到 90%。
  • 代码执行 + MCP：把 MCP 工具呈现为文件系统中的代码 API，Agent 按需读取；示例中 token 从 150,000 降到 2,000（节省 98.7%），还能让敏感数据不经过模型上下文。

核心知识点（摘自 Building effective agents）

  • 两类系统：工作流——LLM 与工具按预定义代码路径编排；Agent——LLM 动态指挥自己的流程与工具使用。

  • 附录中的两个实践：客服（对话 + 工具 + 以“解决率”计费）与编码 Agent（可用自动化测试验证）。

多 Agent 系统（摘自 How we built our multi-agent research system）

  • 以 Opus 4 为主 Agent、Sonnet 4 为子代理的多 Agent 系统，在内部研究评测上比单 Agent Opus 4 高出 90.2%。

  • 提示原则：教会编排者如何委派（目标、输出格式、工具、边界）；按查询复杂度调整投入；让 Agent 自我改进提示与工具描述。

M7 评测（Evals）与护栏

学时：8阶段：质量与生产对应认证：Architect Professional

学习目标

  • 能为 Agent 从零建立评测体系，并把它作为模型升级、提示修改、上线决策的依据。
  • 能设计幻觉、越狱、提示泄露等风险的护栏。

核心知识点（摘自 Demystifying evals for AI agents）

  • 三类评分器：基于代码（精确匹配、单元测试、状态检查，快且客观）、基于模型（量表打分、成对比较，灵活但需校准）、人工（金标准，成本高）。
  • 能力评测 vs 回归评测：前者衡量“能做到什么”，后者保证“已经能做的不退化”。
  • pass@k vs pass^k：pass@k 是 k 次中至少成功一次的概率，适合“成功一次就够”的工具；pass^k 是 k 次全部成功的概率，适合要求稳定一致的 Agent。
  • 从 0 到 1 的路线图：Step 0 尽早开始 → 1 从已经在手工测试的内容入手 → 2 写无歧义且带参考答案的任务 → 3 构建正反平衡的问题集 → 4 搭建环境稳定的评测 harness → 5 认真设计评分器 → 6 阅读运行记录（transcripts） → 7 监控能力评测饱和 → 8 通过开放贡献长期维护评测集。
  • 小样本起步：多 Agent 研究系统团队最初只用约 20 条代表真实用法的查询；早期一个提示改动就能让成功率从 30% 提升到 80%，少量用例即可看出差异。

案例 1 Zendesk：用 Agent SDK 构建“客户自定义 Agent”平台

交付方法论：Custom agent development关联模块：M0、M5、M6、M7、M9

7 周 100 万次执行人工处理时长最多 -80%5 人团队 4 个月 PoC→早期访问一客户 99% 准确率去重

背景

Zendesk 已经能自动处理大量客户请求，难点在“首次消息与最终结果之间”的工作：退货政策例外、复杂保修索赔、详细账单问题。小公司靠人工逐单处理，大公司的 AI 团队只能做一次性自动化，覆盖最简单的情况。

做法

  • 选型靠评测：内部测试系统按 15 项指标、用客户真实编写的那类 Agent 评估各家模型，每次新模型发布都重跑；选择 Sonnet 的原因包括 PDF 阅读表现好、达成决策所需的规划轮数更少，并强调看“单任务成本”。
  • 部署渠道服从治理：通过 Amazon Bedrock 在既有 AWS 区域运行，满足数据驻留与治理要求。
  • 产品形态：客户用自然语言写 Agent 指令，几次点击接入 Zendesk 动作与 Jira、Google Drive 等外部工具；过去需数月工程的工作约 30 分钟配置完成。例如事故分诊：发现相似工单激增 → 建 Jira → 在 Slack 通知工程师 → 告知受影响客户 → 修复后批量关单并说明原因。
  • 架构：路由器把简单请求交给单次调用，复杂请求进入“先规划后执行”的流程；每次运行后 Agent 复盘并把经验保存为 Skill。
  • 控制与可观测：客户决定每个 Agent 可执行哪些动作；提供完整工具调用日志、模拟对话与 A/B 测试。

讨论题

  1. 如果客户只看 token 单价而倾向更便宜的模型，你如何用“单任务成本”说服对方？需要哪些数据？
  2. “自然语言编写 Agent”把配置权交给了业务用户，FDE 需要设计哪些护栏与权限控制？
  3. “Agent 把经验保存为 Skill”会带来哪些质量与安全风险？如何纳入评测？
